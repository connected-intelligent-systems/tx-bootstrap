# Release 0.4.0

This release fixes security issues in the federated catalog and the
participant portal, and changes how the tunnel ingress finds participant
routes. Tunnel deployments need new settings before upgrading. Packages,
images, Compose artifacts, and Helm charts share version `0.4.0`.

## Security fixes

- **SPARQL `SERVICE` could reach internal hosts.** A query could get a
  `SERVICE` clause past the catalog's query filter and make the catalog send
  HTTP requests to any address, including internal services. SPARQL queries
  now run in a separate process that, on Linux, cannot open network sockets.
- **One SPARQL query could stall the catalog.** A timed-out query kept running
  and blocked the health checks, which led to restarts. Queries now run against
  a read-only snapshot and are stopped at `SPARQL_TIMEOUT_SECONDS`.
- **Provider data could run script in the portal.** Responses from the data
  proxy (`/api/data/...`) could carry their own browser security headers and
  run in the portal origin. Provider content is now sandboxed: it cannot run
  scripts or relax the portal's policies, and it cannot be loaded as a script,
  style sheet, worker, or frame. Transfer downloads are always offered as files.
- **One participant could stop catalog crawling for everyone.** A DSP endpoint
  containing characters such as `{` or `|` was accepted but broke catalog
  synchronization for all participants. Such URLs are now rejected, and the
  crawler skips invalid entries.

## Changes

- The tunnel ingress reads approved routes from a new authenticated console
  endpoint, `/api/network/tunnel-routes`. Public hostnames route only to nodes
  enrolled with a verified participant's key; names chosen by participant
  clients are no longer trusted.
- Interrupted tunnel key creation is cleaned up automatically and recorded in
  the participant's history.
- New federated catalog settings: `SPARQL_NETWORK_SANDBOX` and
  `FEDERATED_CATALOG_SNAPSHOT_PATH`. See
  [Federated catalog](../../apps/federated-catalog/README.md#sparql-isolation).

## Upgrade

Select matching `0.4.0` images and deployment artifacts. No database
migrations.

**Tunnel deployments:** configure the routing settings before starting the new
ingress; an ingress without a routing token does not start.

1. Generate a separate random token of at least 32 characters. Do not reuse an
   administrative API key.
2. Set it as `HEADSCALE_ROUTING_API_KEY` on the operator console (Helm:
   `existingSecret.keys.headscaleRoutingApiKey`) and as
   `TUNNEL_ROUTING_API_KEY` on the ingress.
3. Set `TUNNEL_ROUTING_API_URL` on the ingress to
   `https://<console-host>/api/network/tunnel-routes`.

See [Participant tunnel](../participant-tunnel.md#deploy) for details.

**Federated catalog:** SPARQL now needs Linux seccomp, which standard Docker
and Kubernetes runtimes provide. Where it is unavailable (for example gVisor),
SPARQL requests return HTTP 500 and the catalog logs the reason; dataset search
is unaffected. Query snapshots are stored next to the catalog store, on the
same volume, so existing volume mounts work unchanged.

**Clients:** SPARQL queries that use `SERVICE` now fail. Browser requests that
load data proxy responses as scripts or style sheets receive HTTP 403.
