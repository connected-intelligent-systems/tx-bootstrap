# Release 0.5.0

This release moves the stack to Tractus-X EDC 0.13.0 and the matching
Eclipse EDC 0.17.0 identity components. Packages, images, Compose artifacts,
and Helm charts share version `0.5.0`.

## Component versions

| Component                                | 0.4.x  | 0.5.0  |
| ---------------------------------------- | ------ | ------ |
| Tractus-X EDC (control plane, dataplane) | 0.12.1 | 0.13.0 |
| IdentityHub                              | 0.3.2  | 0.4.1  |
| IssuerService                            | 0.3.2  | 0.4.1  |
| BDRS server                              | 0.5.7  | 0.6.0  |

## Changes

- IdentityHub and IssuerService 0.4 take participant context IDs unencoded in
  all URLs, including the public credential service endpoint
  (`/api/credentials/v1/participants/<BPN>`). The base64 settings are gone:
  `PARTICIPANT_BPN_BASE64`, `BPN_ISSUER_BASE64`, `ISSUER_CONTEXT_PATH_ID`,
  `IDENTITYHUB_PARTICIPANT_CONTEXT_PATH_ID` and the Helm values
  `identity.participantBpnBase64` and `identity.issuerBpnBase64`.
- Participant init corrects the service endpoints of an existing participant's
  DID document when they differ from the configured ones (for example after
  this upgrade or a change of public host).
- Participant init no longer retries indefinitely when the DID document stays
  without the participant key; it fails after `DID_DOCUMENT_ATTEMPTS`.
- Connector settings use the renamed DCP keys
  (`TX_EDC_IAM_DCP_*`, formerly `TX_EDC_IAM_IATP_*`).
- The EDC's built-in federated catalog API (port 8082, `/api/catalog`) is
  gone in Tractus-X EDC 0.13.0 and is no longer configured or exposed. The
  tx-bootstrap federated catalog is unaffected.
- The dataplane's participant ID is now the participant's DID, as in the
  upstream 0.13.0 chart.
- The participant API's OpenAPI description is generated from the Tractus-X
  EDC 0.13.0 control-plane API. The gateway still uses the `/v3` management
  API, which upstream now marks as deprecated.
- The optional S3 HTTP-pull dataplane image is rebuilt on Tractus-X EDC
  0.13.0.

## Dataspace Protocol 2025-1

- The portal and the federated catalog choose the protocol version per
  counterparty through the EDC connector discovery API
  (`/v3/connectordiscovery/dspversionparams`). Between 0.5.0 participants this
  is DSP 2025-1 at `<DSP address>/2025-1`; when discovery fails, they fall
  back to DSP 0.8, which 0.13.0 still serves. Participants keep publishing
  their unversioned DSP address.
- A protocol entered explicitly in the portal's negotiation and transfer forms
  is used as is. Data access requests remember the protocol of their
  negotiation.
- The participant API allows the discovery operation with the `catalog:read`
  scope.
- DSP 2025-1 catalogs identify the provider by DID instead of BPN, and the
  negotiation's `assigner` is the provider DID. API clients that build
  requests themselves must use discovery or keep sending
  `dataspace-protocol-http` (0.8).
- The JSON-LD contexts of DSP 2025-1, the EDC DSP namespace, and Tractus-X
  auth are bundled with the portal and the federated catalog, so neither
  fetches them at run time.

## Token refresh

Tractus-X EDC 0.13.0 keeps a superseded refresh token valid until its
successor is used. The data proxy repeats a failed refresh once, so a lost
refresh response no longer breaks access to a transfer.

## Usage policies

- The portal's Tractus-X policy editor follows the constraint rules that
  Tractus-X EDC 0.13.0 enforces: the allowed operators per constraint (mostly
  `eq`), the fixed values as choices, and end dates as timestamps (a date
  without a time means the end of that day, UTC).
- A new template, **Usage period**, limits use to 30 days after the
  agreement. `DataUsageEndDate` and `DataUsageEndDurationDays` are enforced
  when a transfer starts; the upstream policy monitor also checks them for
  running transfers. The contract is still concluded under an expired period.
- The portal shows when the usage period of an agreement ends. Data access
  whose period has ended has the new status **Expired** (also a filter on the
  data access list) and no longer offers **Use data**. The offer dialog warns
  when an offer's usage end date has already passed.
- Refused or failed transfers show the provider's reason in the transfer list
  and no longer offer access details.
- Numeric values are sent as strings; the 0.13.0 policy validator rejects
  number literals with HTTP 500.
- The local end-to-end test checks DSP 2025-1 discovery, EDR refresh, and the
  rejection of a transfer under an expired usage end date.

## Using data in the portal

- **Use data** starts access directly: the portal starts an HTTP-pull transfer
  for the current agreement, or reuses the one already running, without asking
  for a transfer type. On the data access list it opens the access record and
  starts access there.
- The access record has an **Access** tab: progress while the provider starts
  the transfer, then the proxy path, preview and download, and direct EDR
  access; or the provider's reason if it refused. **Use data** opens it.
- Transfers to an HTTP endpoint, Amazon S3, or Azure Blob Storage are started
  with **Transfer to…**; the transfer list opens afterwards.

## Upgrade

Select matching `0.5.0` images and deployment artifacts and upgrade the
operator and all participants together.

- Remove the base64 settings listed above from your environment files and
  Helm values; an explicit `PUBLIC_CREDENTIAL_SERVICE_ENDPOINT` or
  `publicEndpoints.credentialServiceEndpoint` must end in the plain BPN.
  Participants' DID documents are corrected on the first start of
  participant init.
- **Operators upgrading an existing deployment:** the issuer's DID document
  still advertises its IssuerService endpoint with the base64-encoded issuer
  BPN, so participants cannot request credentials. IssuerService has no API to
  change it; after upgrading, update it in the IssuerService database (`issuer`
  in the local Compose setup):

  ```sql
  UPDATE did_resources
     SET did_document = replace(did_document::text,
           '/participants/<base64 issuer BPN>', '/participants/<issuer BPN>')::json
   WHERE did = '<issuer DID>';
  ```

- On first start, the control plane's database migration drops the
  `edc_federated_catalog` table (upstream EDC federated catalog cache; it holds
  no tx-bootstrap data).
- Custom settings that still use `TX_EDC_IAM_IATP_*`, `WEB_HTTP_CATALOG_*`,
  `EDC_DATASOURCE_BPN_NAME` or `EDC_DATASOURCE_EDR_NAME` must be renamed or
  removed; see the upstream
  [migration guide](https://github.com/eclipse-tractusx/tractusx-edc/blob/0.13.0/docs/migration/2026_06-Version_0.12.x_0.13.x.md).
- Clients calling the removed EDC management endpoints (`/v2/edrs`,
  unversioned `/business-partner-groups`, `/v4alpha/...`) must use the `/v3`
  equivalents.
